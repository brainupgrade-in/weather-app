# Building Features Guide

This guide describes the repeatable feature workflow used for WAPP-001 Weather Lookup and WAPP-002 Temperature Unit Toggle. After setup, the intended human intervention is limited to reviewing and merging pull requests.

## Lifecycle at a glance

```text
Jira Story
  -> approved specification PR
  -> specification PR merged
  -> implementation dispatch
  -> GitHub issue with agent-ready
  -> Jira In Progress
  -> Copilot implementation
  -> draft implementation PR
  -> CI and human review
  -> merge
  -> Jira Done
```

Jira is the source of truth for requirements, priority, ownership, and status. GitHub is the source of truth for code, pull requests, CI, and agent execution.

## 1. Choose the next feature

Start from an open question, a user problem, or a clearly bounded improvement. Prefer one independently testable behavior per feature.

For the Weather App, the first feature was `WAPP-001` Weather Lookup. Its open question about Celsius versus Fahrenheit became `WAPP-002` Temperature Unit Toggle.

Before creating work, check:

- Is the behavior separate from existing scope?
- Can acceptance criteria be written as observable outcomes?
- Can it be implemented without changing unrelated contracts?
- Is there an existing specification or decision that constrains it?

Avoid starting with a vague request such as `make the weather better`. Write a concrete outcome instead.

## 2. Write the specification

Create a new numbered directory under `specs/`:

```text
specs/003-your-feature/
  spec.md
  plan.md
```

The specification should contain:

- Feature ID, for example `WAPP-003`.
- User story.
- In-scope and out-of-scope behavior.
- Functional requirements.
- Non-functional requirements when relevant.
- API or UI contract.
- Acceptance criteria.
- Risks and open questions.

Keep the specification testable. Example acceptance criteria from WAPP-002:

- A fresh page displays Celsius by default.
- Selecting Fahrenheit converts the current displayed value.
- The selection is restored from `sessionStorage`.
- Switching units does not issue another provider request.
- The control is keyboard accessible.

Update `specs/README.md` with a link to the new specification.

## 3. Create the Jira Story

Create a Story in Jira project `WAPP`:

- Summary: short feature name.
- Description: user story, scope, acceptance criteria, and links to the repository spec and plan.
- Labels: `github-synced` initially.
- Status: `To Do`.

Use the actual Jira key in all related artifacts. The key is generated by Jira, for example `WAPP-2`; the repository feature ID can be `WAPP-002` when that numbering convention is used.

Do not mark the issue `Agent-ready` yet. The agent should not implement a requirement before its specification is available on `main`.

## 4. Open the specification PR

Create a branch and commit only the specification and supporting plan:

```bash
git switch -c feat/wapp-003-your-feature-spec
git add specs/003-your-feature specs/README.md
git diff --cached --check
git commit -m "Specify WAPP-003 your feature"
git push --set-upstream origin feat/wapp-003-your-feature-spec
```

Open a PR whose title starts with the Jira key:

```text
[WAPP-3] Specify your feature
```

This title matters because `spec-merged-dispatch.yml` uses the Jira key in the merged specification PR title to retrieve the Jira issue and dispatch implementation.

The specification PR is the first review boundary. Reviewers check scope and acceptance criteria, not implementation code.

## 5. Review and merge the specification PR

Wait for CI, review the specification, and merge the PR. After merge:

1. `spec-merged-dispatch.yml` reads the Jira issue.
2. It sends a `jira-ready-for-development` repository dispatch.
3. `jira-ready-dispatch.yml` creates a GitHub issue with the Jira key.
4. The GitHub issue receives `agent-ready` as a separate label event.
5. Jira transitions to `In Progress` when the agent handoff starts.

The separate label event is intentional. It triggers the `issues:labeled` agent workflow reliably.

## 6. Let the agent implement

The implementation workflow reads:

- The GitHub issue.
- The linked Jira description.
- The specification on `main`.
- The relevant implementation plan.

It should:

- Inspect the existing code before editing.
- Follow the plan's test strategy.
- Keep the API contract stable unless the specification explicitly changes it.
- Run focused tests.
- Open one draft PR with the Jira key in the title.
- Report changed files, tests, and unresolved risks.

The agent is restricted by `allowed-files`. It may modify application, tests, specifications, documentation, and approved manifests, but not workflow files or credentials.

No manual code changes are required at this stage.

## 7. Review the implementation PR

When the draft PR appears:

1. Check that the PR title contains the Jira key.
2. Compare the implementation against the acceptance criteria.
3. Inspect the tests and confirm external calls are mocked where required.
4. Confirm CI passes, especially `Tests / tests`.
5. Check that no secrets or unrelated files were changed.
6. Resolve review comments.
7. Approve and merge the PR.

The human review and merge are the safety gate. Do not allow the agent to merge its own PR.

## 8. Automatic completion

When the implementation PR is merged, `jira-pr-status.yml`:

1. Extracts the Jira key from the PR title.
2. Looks up the Jira project's `Done` transition.
3. Transitions the Jira issue to `Done`.
4. Adds the merged PR link as a Jira comment.

If a PR is closed without merging, Jira receives a status comment but is not automatically marked Done.

## 9. Verify the feature after merge

Update local `main` and run the application:

```bash
git switch main
git pull --ff-only origin main
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt pytest
python -m pytest
python app.py
```

Exercise the feature manually in a browser. For Weather Lookup, verify known, unknown, and empty-city behavior. For a UI feature such as WAPP-002, verify fresh-session defaults, switching, reload persistence, and no duplicate provider request.

Record any follow-up as a new Jira Story or Bug rather than silently expanding the merged feature.

## 10. Troubleshooting

### GitHub issue exists but the agent did not start

Remove and re-add the `agent-ready` label. The implementation workflow listens for a distinct `issues:labeled` event.

### Agent created an issue instead of a PR

Inspect the agent run's safe-output logs. Common causes are:

- GitHub Actions is not allowed to create pull requests.
- A generated file is outside `create-pull-request.allowed-files`.
- A protected file triggered review fallback.
- The agent produced `noop` because requirements were incomplete.

Fix the workflow policy, merge the fix, and retrigger `agent-ready`.

### Jira did not move to In Progress or Done

Check that the Jira project has statuses named exactly `In Progress` and `Done`, and that the integration account can transition issues. Check the PR title contains the Jira key.

### CI cannot import the application

The repository test workflow sets `PYTHONPATH: .`. Confirm the change is on the PR branch and rerun the checks.

### PR is behind main

Update the feature branch from `origin/main`, resolve conflicts, push, and rerun CI. Do not force-push shared workshop branches.

## Workshop completion checklist

- [ ] Jira Story created in `WAPP`.
- [ ] Feature specification and plan added under `specs/`.
- [ ] Specification PR title contains the Jira key.
- [ ] Specification PR reviewed and merged.
- [ ] GitHub issue created and labeled `agent-ready`.
- [ ] Jira status changed to `In Progress`.
- [ ] Agent draft implementation PR created.
- [ ] CI passed and implementation PR reviewed.
- [ ] Implementation PR merged.
- [ ] Jira issue automatically changed to `Done`.
- [ ] Feature manually verified on updated `main`.
